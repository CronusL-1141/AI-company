# Codex 账号用量监控：增量摘要与空闲门控

本文是账号用量监控（`services/account_monitor.py`）读取路径与采样节奏的规格来源，对应任务 551aee38，随 v1.15.0 发布。套餐估算的算术本身（周期锚点、按 request_id 去重、Spark 独立计量、缺失即断段）沿用原有规则，本文不改它，只规定这些值如何维护、何时重建、何时采样。

## 1 背景

2026-09-29 取证：监控按用户设定的 30 秒间隔采样，每一轮都在 API 事件循环上把该账号的套餐与价格历史全量读三遍（约 1.8 万行 JSON，经 ORM 物化再逐行校验），只为取「最新一条」或「本周期累计」。每轮阻塞循环 2 到 19 秒，其中四到六成是 GC；`/api/health` 与 hook 请求在负载下卡 10 到 47 秒。账号用量页的详情接口每次刷新也做同样的全量读，并把全部额度历史（5.7MB）返回给页面。

缺陷随 v1.14.0 引入，不随版本变化，只随历史行数线性恶化。

## 2 增量派生表

历史样本只追加、不改写，每个派生值只取决于「上一步的状态」和「下一条样本」。所以把这些值存成一份小状态，写入一条样本就推进一步，读取时不再折叠历史。

### 2.1 两张表

| 表 | 主键 | 内容 |
|---|---|---|
| `account_plan_summaries` | (account_key, kind) | kind 为 `plan` 或 `price`。payload 是一份带版本号的摘要：表指纹（该账号的行数、按 (observed_at, id) 排序的最新行 id），以及每个额度窗口 (limit_id, window_duration_ms) 的状态 |
| `account_plan_cycle_requests` | (account_key, limit_id, window_duration_ms, kind, request_id) | 当前价格周期里已计入的 request_id，即去重集合；kind 为 `auto`（自动周期）或 `manual`（从已保存锚点起算的周期） |

窗口状态：

- 价格窗口：最新一行的 id、观测时间与已用百分比；自动周期状态（锚点行的 id、时间、百分比，本周期已知金额的 Decimal 字符串，计价元数据，reason，假定档位与已计价的请求数）；手动锚点周期状态及其对应的锚点 (snapshot_id, revision)。
- 套餐窗口：最新一行的 id 与观测时间，以及本地 token 连续链的起点行 id。

### 2.2 一个步进函数，三条路径

`services/plan_summary.py` 的 `advance_cycle`（价格周期）与 `advance_run_start`（token 链起点）是唯一的算术来源：

1. 全量函数（`plan_pricing` / `plan_capacity`）在排好序的列表上折叠同一个步进函数；
2. 写入路径（`_add_plan_snapshot` / `_add_pricing_plan_snapshot`）在插入同一事务里走一步并写回摘要；
3. 重建子进程在数据库快照上折叠同一个步进函数。

三条路径算术相同，存下来的 Decimal 字符串逐字相等，不只是数值相等。带 prediction 的价格行，插入时的校验改为「上一条的周期累计加这一步」，与旧的「从周期锚点全量重算」逐条相等。

### 2.3 何时采信，何时重建

读取方只在两个条件同时成立时采信摘要：

- 表指纹一致：摘要记录的 (行数, 最新行 id) 等于表里的实际值；
- 锚点一致：摘要折叠时依据的锚点 (snapshot_id, revision) 等于锚点表里当前的锚点。

以下情况摘要失效，由下一个读取方触发重建：

- 升级后首次使用（有样本、没有摘要）；
- 乱序插入：新行排在窗口最新行之前（例如系统时钟回拨）。不带 prediction 的乱序行照常写入并作废摘要；带 prediction 的写入在摘要失效期间一律拒收，报错与原来相同；
- 绕开维护路径写入的行（旧版本代码、手工写库），由表指纹对不上识别；
- 摘要版本号未知。

采集路径每轮先取摘要（必要时等重建完成）再计算 prediction，所以监控轮次不会撞上「失效期间拒收」。

### 2.4 重建协议

- 在一次性子解释器里做（`sys.executable -c`，从父进程自己的源码树导入同一模块，保证两边代码一致），只读连接读样本、折叠、把结果以 JSON 写到 stdout，算完即退。不建池、不常驻。
- 父进程在 `BEGIN IMMEDIATE` 下复核表指纹与锚点；期间若有新写入就丢弃结果重做，最多 3 次。
- 同一 (事件循环, 数据库, 账号) 同时只跑一个重建，并发读取方共享结果；重建任务被 shield，调用方超时或取消不会中断它，下一个读取方直接拿到存好的结果。
- 子进程超时 120 秒，与记忆整理的配对子进程一致。生产副本上 1.8 万行的重建耗时约 2 秒，负载下放大十倍也在限内；超时后由 `subprocess.run` 杀掉并回收。
- 内存数据库直接拒绝，不在循环上折叠。

### 2.5 失败语义：基础设施与数据分开

- 摘要不可用（`SummaryUnavailableError`：子进程起不来、超时、崩溃、输出畸形，重建期间表一直在变，摘要指向的行不存在）属于基础设施失败。它刻意不是 `ValueError`：监控轮次按错误结束，不写库，下一轮重试；手动采样、锚点重置与详情接口返回 503。
- 数据层面的缺口（本地日志读不到或不完整、采样期间来源变化、`ValueError` 类的校验失败）保持原有「失败即断段、不报假零」的语义：保存不可用的价格行，本周期标为对应的 reason。

分开的理由：如果把基础设施失败也存成不可用价格行，本周期的 reason 会一直停在 `pricing_unavailable`，直到下一次额度重置（周窗口最长 7 天），而这段时间里数据本身并没有缺口。

### 2.6 派生数据可删可重建

两张表只从不可变样本派生，任何时候整体删掉，下一次读取都会从样本重建出逐字节相同的内容；它们不是任何数据的唯一副本，也不计入锚点重置的证据集。清理数据库时可以删，但删了没有收益：下一次读取会付一次重建的代价。

### 2.7 热路径只做有界读取

监控轮次与账号用量页只调用以下读取，每个的开销与历史长度无关：窗口最新一条（`latest_plan_snapshot`、`get_*_snapshot`）、摘要、候选请求 id 的去重命中、窗口起点之后的前几行（token 链起点早于窗口起点时）、最新额度观测（`latest_quota_observation`）、分页（`page_snapshots`）与计数。`list_*` 全量读取保留给工具与测试，热路径不再调用。

表指纹里的 `COUNT(*)` 随行数线性增长，1.8 万行约 1 毫秒，目前可以接受。

## 3 空闲门控

### 3.1 裁定

缔造者 2026-09-29 原话：「这个不是读的codex的么？又不是我们的CC，没有新的输入输出应该不继续读才对，而且应该读取增量才对」。

据此：本机 Codex 没有新活动时不采样；读取一律改为增量（见第 2 节）。

同日 23:30 裁定兜底间隔为 2 小时：Codex 额度由整个账号共用，别的设备上的用量本机看不到活动，所以空闲时仍要定期读一次原生额度。代价是本机空闲期间，别的设备上用掉的额度最多约晚 2 小时（再加一个采样间隔）才出现在页面上，缔造者已接受。

### 3.2 规则

到期的采样轮次先问一句「上次成功采样之后，本机 Codex 有没有写过会话日志」：

- 信号：`$CODEX_HOME`（默认 `~/.codex`）下 `sessions` 与 `archived_sessions` 里 `*.jsonl` 的最新修改时间，是否晚于上次成功采样（最新一条额度观测的 observed_at）。采集在时刻 T 已读完 T 之前写入的所有行，所以「T 之后有文件被写过」恰好等于「有新东西可读」。遍历在工作线程里做，约 500 个文件几毫秒；不跟随符号链接。
- 没有写入就跳过本轮：不启动原生读取、不扫本地日志、不写样本。状态、上次开始时间与上次错误恢复到抢占之前的样子，下次到期时间设为「现在加一个间隔」，并记下 `last_skipped_at`。
- 以下情况照常采样：
  - 距上次成功采样满 2 小时；
  - 上次采样报告的任一额度窗口的 `resets_at` 已过，以便及时看到周期重置；
  - 上次成功采样的时间晚于现在：系统时钟回拨过，之后写入的日志时间不能再和它比较；
  - 信号查不清：没有探针、没有过往采样、目录缺失、遍历出错、条目超过 5 万。
- 手动采样和登录变化后的核验不经过门控。
- 门控只会少采、不会多采：本机有活动时仍按用户设定的间隔采样。

「日志时间晚于现在」不需要单独判断：若上次采样不晚于现在，这样的写入必然晚于上次采样，本来就算作有活动。

### 3.3 为什么不用其它信号

- 使用量记录器已入库的观测：记录器每 5 秒扫一批文件，扫完约 470 个文件要 75 秒左右，信号会滞后；它还会把上一轮已经读过、只是入库较晚的行算成新活动。
- 记录器的游标：同样受记录器节奏限制。

### 3.4 效果

按生产库最近 7 天的采样时间线回放（以区间内有已计价请求近似「有活动」；实际按 mtime，任何写入都算活动，真实跳过率会略低）：10,647 个到期轮次中，2 小时兜底会跳过 10,225 个（96%）；30 分钟兜底为 95%。

## 4 接口变更

- `GET /api/account-usage/{account_key}` 不再返回全量 `snapshots`，改为摘要：`snapshot_count`、`latest_snapshots`（最近一次采样的各额度窗口）、批次估算 `estimates`、`plan_estimates`、`pricing_plan_estimates`。摘要无法更新时返回 503。响应从 5.7MB 降到约 4.5KB。
- 新增 `GET /api/account-usage/{account_key}/snapshots?limit=&before=`：额度观测分页，最新在前；`limit` 为 1 到 500，默认 100；把返回的 `next_cursor`（形如 `<observed_at ISO>|<snapshot_id>`）原样传回 `before` 取下一页；游标无效返回 422；另带 `total`。
- 监控状态新增字段 `last_skipped_at`。
- `POST /api/account-usage/capture` 与 `POST /api/account-usage/{account_key}/plan-anchor/reset` 在摘要无法更新时返回 503，不再落库或返回 409。
- Dashboard：账号列表轮询从 10 秒改为 60 秒（采样成功后本来就会直接失效它）；只有「有前值、`last_finished_at` 变了、状态不是 error 或 paused」时才刷新估算，首载、空闲跳过与失败轮次都不再重拉详情；监控面板显示「上次空闲跳过」与门控说明。

## 5 升级与回填

- 两张新表由 API 启动时的 `create_all` 建出。没有给已有表加列，所以不涉及 `COLUMNS_TO_ENSURE`，也不写迁移脚本。
- 升级后每个账号第一次被读取时，按 2.3 视为「有样本、没有摘要」，由子进程从现有样本重建。生产副本上两个账号分别约 1.9 秒与 0.8 秒，期间事件循环不受影响；之后每次读取为毫秒级。
- 2026-09-19 15:24 到 15:28 之间，账号 3f8052bd 有 9 行价格样本的 prediction 是按更早的规则写下的。旧代码与新代码对它们算出的值相同，今天两者的插入校验都会拒收这样的新写入；这 9 行作为历史事实原样保留，不改写。
- 回退到旧版本：旧代码不认识这两张表，照常全量读取。之后再升级时，旧代码写入的行会被表指纹识别出来，触发一次重建。

## 6 验证

- 等价：在生产库只读副本上，按 (observed_at, id) 顺序把全部 18,669 行套餐样本与 18,600 行价格样本走新的插入路径重放，每一行的周期状态（锚点、累计值字符串、计价元数据、reason）与 a4bab96 的全量实现逐条相等；已存的 16,293 个 prediction 中 16,284 个与新累计值逐字相等，其余 9 个即第 5 节的历史行；81 个检查点上共 470 个窗口估算的 JSON 全等；增量维护的摘要与子进程重建结果逐字节相等。
- 长期守护：`tests/unit/_oracle_plan_*.py` 冻结了 a4bab96 的全量实现，随机历史逐步比对（`test_plan_summary_equivalence`、`test_plan_summaries`）。
- 事件循环：`test_account_usage_offloop` 用进程内的 loop-lag 探针量详情接口与一轮监控对循环的最长占用，界限是同机一次全量读取耗时的四分之一（下限 50 毫秒）。把全量读取放回去，两例在额外 CPU 负载下连跑 5 次均变红；恢复后同样条件下 5 次均通过。
- 门控：`test_account_monitor_gate` 覆盖空闲跳过、有活动或查不清时采样、2 小时兜底的临界三档、窗口重置、时钟回拨、跳过保留上次错误、API 生命周期确实接上探针。
- 失败语义：`test_local_plan_pricing` 覆盖重建失败时本轮报错不落库、下一轮恢复且估算与全量实现相等，以及时钟回拨时晚到的采样不带 prediction、之后自愈。
