# 任务墙摘要（digest）：一处计算，简报、压缩回注、MCP、巡检与 Dashboard 共用

状态：已实施（2026-09-29，任务 f8157c8d）。施工依据是综合方案报告 aced45d4（三份视角方案：Leader 入口 16b5bf40、Dashboard f746148b、数据与口径 52e75606），裁定见 §2。
范围：项目级任务墙的所有 Leader 入口与 Dashboard 任务页。团队级任务墙（`/api/teams/{id}/task-wall`）只跟着换了排序键 `backlog_sort_key`：待办同分时先上墙的在前；进行中、阻塞的分数都是 0，于是也按新建时间升序排（最早新建的在前，原来是新建倒序），别的不动。

## 0. 一句话

服务端用一个纯函数 `build_task_wall_digest` 算出整面墙的摘要：未关条数按状态 × 期限、近 7 天新建与关闭、停滞与沉底计数、最近动静 5 条、待办最优先 5 条、中长期待办之首、卡住的任务。文本也在服务端渲染（`render_digest_text`，上限 1200 字）。会话开场简报、压缩后回注、MCP `task_list_project`、`/loop` 巡检和 Dashboard 读的都是这一份，数字不会各说各的。

## 1. 问题（2026-09-29 实测）

缔造者原话：「我觉得要设计一套展示不然看起来没任务」「短中长期，你一般看长期么，看任务墙一般能看到中长期任务吗」「这个看任务墙的功能也要进行优化，不能只看这些，应该提示你墙上还有多少个任务，可以不全部展示，但是要统计给你，让你知道，另外展示最近5个和最优先的5个」（任务 memo 40a330d8）。

实测到的毛病：

1. **分页把进行中和阻塞全切了。** `/api/projects/{id}/task-wall` 先按分数排序再截取 `limit` 条，而 `calculate_task_score` 对非 pending 一律给 0 分。待办 57 条、最低 1.6 分，所以进行中 21 条、阻塞 4 条永远排在最后被截掉。简报（limit=20）、`workflow_reminder`（20）、`task_list_project`（50）、Dashboard（50）四处都看不到它们，简报里的「=== 进行中任务 ===」段从来没有渲染过。
2. **统计答非所问。** 简报的「总293任务, 已完成212, 待办56」把已完成算进了总数，进行中和阻塞一个字没有；Dashboard 的「high: 164」也含已完成。
3. **同分时越老越靠后。** 等待加成满 3.5 天封顶，同一格（优先级 × 期限）里老任务分数全相同，同分时沿用仓储的新建倒序，结果越早上墙越靠后。
4. **看不出在动什么、卡在哪。** 任务表没有「最近动静」，60 天没人动的进行中任务和刚开工的一模一样。
5. **压缩检查点的「未完成任务（10）」其实是最新的 10 条进行中**，待办永远进不去；末句让 Leader 用 `taskwall_view` 现查，这个工具不存在。
6. **Dashboard 首屏 1.48MB**：带着 212 条已完成任务的完整行（其中 config 就占 32 万字符），页面只渲染其中 20 条。

## 2. 缔造者裁定（2026-09-29，memo 82b3371b）

| 议题 | 裁定 |
|---|---|
| 方案 | B：服务端 digest，五个入口共用。A（修分页）作为第一个提交，简报在同一批里换成 digest，不出现「进行中任务」段一次灌进 21 行的中间态 |
| 最近 5 条 | 按最近有动静排，新建、有进展、刚关闭的都算，每条标明动作类型 |
| 最优先 5 条 | 现有打分不动，同分时先上墙的排前；不再显示分数，改显示「上墙 N 天」。等待加成保留，不做减法 |
| 中长期 | 简报加一行「中期、长期各自排第一的待办」 |
| 批量核对（当晚改判） | 不要「批量核对不算进展」这条规则：所有 memo 都算动静，不论作者同一时间给几条任务记 memo（缔造者 09-29 当晚裁定，decision memo 记在 f8157c8d）。已知代价：一次批量核对之后，被核对到的进行中任务停滞计时全部清零，停滞数会归零；「最近动静」会被这次核对刷屏，最近 5 条全是核对的 memo |
| 停滞与沉底 | 进行中 7 天没动静算停滞，待办 30 天没动算沉底，都只出计数（推荐默认，无异议） |
| 其余 | C 的其余项（自适应阈值、`task.memo_added` 事件）收尾时另建任务；原 C 项里的「memo 核对显式标记」随批量核对规则一起取消 |
| memo 读取（当晚追加） | 只读还在墙上、没完成的任务的 memo；已完成的任务一律不读 memo，「最近动静」里的关闭与近 7 天关闭数用 completed_at 或状态变更时间；状态变更只查未完成任务与近 7 天内关闭的任务。查询开销只随墙上未完成任务数与近期窗口增长，与历史 memo 总数无关 |

## 3. 口径（写进 docstring，由单测钉住）

| 项 | 定义 |
|---|---|
| 范围 | 当前项目、`parent_id` 为空的顶层任务。`project_id` 为空的孤儿任务不计入任何项目。子任务不单独计数，但它们的工作动作算父任务的动静（见「工作动作」） |
| 未关 | pending / running / blocked / failed。completed 只进 `completed_total`、`closed_7d` 和最近动静 |
| 工作动作 | 任务自己的新建、开工、完成时间戳；每一次状态变更；每条 memo，除了记忆整理的合并条（作者 `reconcile`）；不论作者同一时间给几条任务记了 memo，都算（没有批量核对规则，见 §2）。已失效的 memo 照算（写下它就是动作）。已完成任务的动静只看它自己的新建、开工、完成时间与状态变更，它的 memo 不算它的动静。直接子任务上的 memo 算父任务的 memo，子任务的状态变更算父任务的一次「子任务」动作：流水线类父任务一直是进行中，活由子任务逐阶段推进，不这样算会被误判为停滞（L2 审查 A1） |
| 状态变更 | 只取 `task.updated` 事件里 `data.changes` 含 `status` 的记录（在 SQL 里过滤），状态取事件快照；与上一条同状态的重写不算一次变更。第一条记录之前的「上一条」是任务新建时的状态：没有事件记录新建，按任务自己的时间戳推断，开工时间与新建时间相差不到 1 秒算新建即进行中，完成时间同理，其余算待办（否则给新任务重写一次 pending 会显示成「退回待办」）。`task.status_changed` 事件的 `entity_id` 全空（实测 1390 条全空），不作数据源 |
| 不算动静 | 只改标题、描述、优先级、期限、config 的更新 |
| 动静时间 | 以上各项中最晚的一个；同一时刻取任务生命周期里靠后的一步（关闭 > 状态变更 > memo > 开工 > 新建） |
| 动作类型 | 新建 / 开工 / 转阻塞 / 退回待办 / 失败 / 关闭 / memo（附 memo 类型与作者） |
| 读取范围 | 只查还在墙上的任务（待办、进行中、阻塞、失败）及其直接子任务，已完成任务的 memo 一条不读，它的动静只看它自己那一行（新建、开工、完成时间）。① 未完成任务近 35 天（`ACTIVITY_WINDOW_DAYS`）的 memo 逐条读，只取作者、类型、时间。② 35 天以前只读每个未完成任务最新的 3 条，从中取第一条不是 reconcile 合并条的。两处都走 `idx_memos_task_created`（task_id, created_at），按任务按时间定位，不回扫历史；索引由模型声明，老库启动时补建。③ 状态变更只读未完成任务（含子任务）与近 7 天（`CLOSED_WINDOW_DAYS`）内关闭的任务。35 天长于最长阈值（沉底 30 天），更早的 memo 只可能说明「安静得比任何阈值都久」，停滞、沉底的判定用的仍是完整数据 |
| 停滞 | running 且距动静时间满 7 天（`STALE_RUNNING_DAYS`） |
| 沉底 | pending 且距动静时间满 30 天（`DORMANT_PENDING_DAYS`） |
| 阻塞天数 | 进入阻塞（最近一次转为 blocked 的变更）至今；没有这条记录时从新建算起 |
| 最近 5 条 | 全部顶层任务（含已关闭）按动静时间倒序，每个任务一次 |
| 最优先 5 条 | 待办按 `backlog_sort_key`：现有分数降序，同分按新建时间升序（先上墙的在前）。两面任务墙的待办排序用同一个键 |
| 中长期之首 | 中期、长期里排最前且不在最优先 5 条里的待办各一条；某一档没有就不出 |
| 卡住的 | 阻塞（阻塞最久的在前）、失败、停滞的进行中（闲置最久的在前），全量 |
| 趋势 | 近 7 天新建数、关闭数 |
| 标题 | 服务端 `clean_text` 后截到 30 字；ID 取 8 位前缀 |

阈值依据：本项目 170 条已完成任务在运行期间最长静默 5.6 天，没有超过 7 天的；09-29 的 21 条进行中，闲置天数在 6 天与 9 天之间断开。另一个项目的运行期静默 P95 是 13.3 天，7 天不普适，按项目自适应留给 C 项。

## 4. 架构

```
repository.list_wall_tasks(project_id)        顶层任务，不读 description/result/config
repository.list_task_activity(project_id,     memo（含失效）：近 35 天逐条；更早只取未完成任务各自最新 3 条
            since, closed_since)              + 状态变更：未完成任务与近 7 天关闭的（SQL 里只留 changes 含 status 的）
        │                                      含直接子任务，记在父任务名下；memo 走 idx_memos_task_created，
        │                                      events 按 entity_id 查，写成 +events.type 防走 ix_events_type
        ▼
task_wall_engine.summarize_activity(...)      逐任务动静（纯函数）
task_wall_engine.build_task_wall_digest(...)  统计与各列表（纯函数，now 由调用方给）
task_wall_engine.render_digest_text(...)      中文文本，≤1200 字
        │
        ├─ GET /api/projects/{id}/task-wall/digest?format=json|text   新端点
        ├─ GET /api/projects/{id}/task-wall                            响应内嵌同一份 digest
        └─ GET /api/projects/{id}/summary                              计数与 top_tasks 取自 digest
```

- 任务行（`list_wall_tasks`）仍按项目读全部顶层任务，每任务一行、不读描述与结果：统计已完成数与近 7 天关闭数要用到，随任务总数增长（09-29 为 310 行，约 5ms），与 memo 数无关。
- 模型在 `types.py`：`TaskActivityRecord`（输入）、`DigestItem`、`TaskWallDigest`（输出）。
- JSON 形态里带渲染好的 `text`；`format=text` 只返回这段文本（text/plain）。
- 全部在请求时计算，没有定时器，不加列、不回填。实测 09-29 的库：299 条顶层任务、3947 条动作记录，热缓存整份约 30ms（SQL 约 25ms，计算 3ms），JSON 约 16KB。按当晚的读取范围，同一份库读 888 条（原来全量 3956 条）。放大实测（真实数据加合成 memo，合成的全部挂在已完成任务上，每档 30 次取中位）：已完成任务的 memo 加到 2 万、5 万条（总量 3492 / 23492 / 53492），合成 memo 全在 35 天以前时读取 888 / 888 / 888 条、7.1 / 7.0 / 6.8ms；合成 memo 在一年内均匀分布时同样 888 条、7 到 14ms（首档的 13.7ms 是抖动，30 次的 p90 都在 18ms 以内）；原来的全量读取 3956 / 23956 / 53956 条、16 / 94 / 227ms（均匀分布一组 17 / 118 / 259ms）。每一档的计数、最优先 5、卡住的与各任务闲置天数都与全量读取逐条一致。事件查询写成 `+events.type` 后走 `ix_events_entity_id`，不加 `+` 时规划器会选 `ix_events_type`（测试钉住查询计划，去掉 `+` 用例即红）。
- 文本在服务端渲染：会话简报的 hook 有逐字节副本（`src/aiteam/hooks` 与 `plugin/hooks`，I1），格式放在 hook 里每改一次要同步多份；服务端渲染的文本同时给简报、压缩回注、MCP 与巡检用。

## 5. 各入口

### 5.1 `/api/projects/{id}/task-wall`（提交 A 起）

- `limit`/`offset` 只作用于待办。进行中、阻塞、失败始终全量返回，排在待办之后（先进行中，再阻塞、失败，各自按最近动静倒序）。
- 响应加 `not_shown: {"pending": N}`（这一页没列出的待办数）和 `has_more`。
- 只做「状态优先排序再分页」不行：简报的 limit=20 会被 21 条进行中占满，最优先 5 条变空。
- 提交 B 起：`stats` 改为只数未关的顶层任务（字段名不变，`completed_count` 仍是已完成数）；响应内嵌 `digest`；未关的行带 `last_activity_at/kind/memo_type/by`、`idle_days`、`wall_days`、`stale`、`blocked_days`；`completed_limit`/`completed_offset` 把已完成任务分页成精简行（加 `completed_total`、`completed_has_more`），不传时保持原样；`fields=card` 让未关的行不带 description、result、config（看板卡片用不到，打开详情时单独取）。

### 5.2 会话开场简报（`session_bootstrap.py`，两份副本同步）

- 删掉 `task-wall?limit=20` 的调用、Top5、「统计: 总…」一行和「=== 进行中任务 ===」段，原位放 digest 的文本。取数用 `GET .../task-wall/digest` 的 JSON，取其中 `text`（与 `format=text` 同一段；走已有的 `_api_get`，调用次数不变，2 秒超时）。
- hook 逐行再过一遍 `_sanitize_inline`（I24 允许的清洗落点之一），保留每行的缩进，服务端文本逐字节原样进简报；每行截到 200 字，总量 1600 字保险丝。
- 取不到（不可达、超时、旧 API 没有这个端点返回 404、响应里没有 text）只出一行「任务墙摘要取不到，用 task_list_project 查看」，简报其余部分照常。
- UPS 冷启动补发复用 `startup_context`，自动是同一份。
- 原「进行中任务」段的提醒意图（「请检查这些任务是否需要更新状态或添加 memo」）由停滞计数和 `/loop` 第 2 步接手：这是替换，不是删除。

### 5.3 压缩后回注（`compact_checkpoint.py`）

压缩后的 SessionStart(compact) 注入的是「简报 + 检查点」，简报里已经带着实时的 digest。`render()` 不再输出「未完成任务」段（快照里的 `open_tasks` 照采留档，不删数据）；只有这一块时检查点整段不出；末句改为「任务墙以上方简报里的任务墙摘要为准」，`taskwall_view` 改成 `task_list_project`。

### 5.4 MCP `task_list_project`

项目范围的精简视图第一项是 `digest`（与简报同一段文本），`fields="all"` 时是完整 JSON。行里的停滞任务带 `stale` 与 `idle_days`。`hint` 说明：digest 是全墙；wall 是一页待办（limit 只管待办，not_shown 是没列出的条数）加全部进行中、阻塞。`workflow_reminder` 的派工核对不用改代码：进行中任务现在就在返回里，派去做进行中任务不会再误报「未匹配到任务墙项」。

### 5.5 `/loop` 巡检与 `/os-task`

- `plugin/loop.md` 第 2 步：`task_list_project()` 开头的 digest 就是全墙统计与最近 5 条、最优先 5 条，从最优先的里挑；digest 报「进行中 N 条超 7 天没动静」时，本会话用 `task_list_project(status="running")` 把 `stale` 的逐条补 memo 或改状态，处理过的不必每轮重复。模板标记 v1 不改，install 会覆盖没被用户改过的副本。
- `/os-task`：先原样展示 digest，再按需展开 wall；删掉「这个排序就是答案，不要自行重排」。

### 5.6 Dashboard 任务页

- 上半部分：统计条（未关按期限、进行中、停滞、阻塞、待办与沉底、近 7 天），每格点一下筛选下方三栏，再点取消；三块总览：最近动静（时间 · 动作 · 标题 · 状态）、最优先 5（优先级 · 标题 · 上墙天数）、卡住了（阻塞 N 天 / 停滞 N 天，默认 5 行可展开）。
- 下半部分：短中长三栏，栏头写「进行中 a · 阻塞 b · 待办 c」；每栏按进行中（按最近动静，停滞的折成「另有 N 条进行中已停滞」）、阻塞与失败、待办（按分数，默认露 8 张，其余折成「还有 N 条待办」）分节。每条未关任务要么是卡片，要么在某个折叠计数里。
- 卡片：标题两行、优先级徽标、一行「状态 · 动作 时间 · 作者」，待办显示上墙天数，停滞琥珀色，阻塞玫红色。描述和标签只在详情里。
- 已完成：默认折叠，标题「已完成 N · 近 7 天 M」（取自 digest），展开后每次加载 50 条精简行、按天分组。
- 首屏载荷：原来 `task-wall?include_completed=true&limit=50` 1,513,920 字节（a4bab96 的代码）；现在 `task-wall?limit=500&fields=card` 81,242 字节（同一份 09-29 21:34 快照）。
- 实时刷新：一次 task 事件只让任务墙这一个查询失效（它内嵌 digest），并且任务墙每 3 秒最多刷新一次，一串事件最后会补刷一次（`useRealtimeEvents` 的 `MIN_REFRESH_INTERVAL_MS`）。已完成列表用独立的查询键，只在任务墙带回的已完成数变化时才重拉；总览页项目卡的 digest 挂在 `projects` 前缀下，和原来一样只随项目事件刷新。这样一次任务事件不会同时拉任务墙、digest、已完成各页和 N 张项目卡。
- 总览页的项目卡片改读 `/task-wall/digest`（约 16KB），进度 = 已完成 /（已完成 + 未关）；原来每张卡拉一遍带全部已完成行的任务墙。
- 「近 7 天」一格：非零时带符号（+N / −M），为 0 时只写 0。
- 中英双语文案都在 `i18n/zh.ts`、`i18n/en.ts` 的 `tasks` 段。

## 6. 简报任务段样例

09-29 快照上的真实计数，标题与 ID 换成了中性示例（957 字，15 行；上限 1200 字）：

```
=== 任务墙：未关 82 条，下列其中 10 条；全墙用 task_list_project（可按 status/horizon 筛） ===
  进行中 17（短7/中9/长1） · 待办 61（短22/中37/长2） · 阻塞 4（短2/中2）
  近 7 天新建 64、关闭 41 · 进行中 14 条超 7 天没动静 · 阻塞最久 19 天 · 待办 15 条超 30 天没人碰
最近动静 5：
  49分钟前·关闭 [medium/mid·已关闭] 发版前复核清单：版本号七处锁步与双语更新说明逐条核对 #1a2b3c01
```

## 8. 风险

1. 没有批量核对规则（缔造者 09-29 当晚裁定）：一次批量核对（例如 09-29 七个 agent 两分钟内给 80 条任务各记一条进度）之后，被核对到的进行中任务停滞计时清零、停滞数归零，「最近动静」5 条全被这次核对占满。停滞要等核对之后再安静满 7 天才重新露出来。
2. 停滞计数会一直带着长跑的研究类任务：不加豁免标签（豁免会变成藏东西的口子），靠诚实改状态消化。
3. 7 天阈值对别的项目不普适，自适应阈值见 §9。
4. `task_list_project` 的返回变了：进行中、阻塞现在都在返回里，「第一行就是最高分待办」的旧习惯改看 digest（待办仍排在每组最前）。
5. 版本错配：新 hook 配旧 API 拿到 404，简报降成一行；旧 hook 配新 API 仍按原来的 task-wall 查询工作，只是其 Top5 同分顺序变成先上墙的在前。
6. 简报里的 ID 是 8 位前缀，任务相关工具目前只收完整 ID；要用某条任务时先从 `task_list_project` 的行里取完整 ID（前缀解析是加法，未做，见 §9）。
